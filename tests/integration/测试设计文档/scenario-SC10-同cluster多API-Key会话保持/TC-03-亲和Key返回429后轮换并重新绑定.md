# TC-03 亲和 Key 返回 429 后轮换并重新绑定

## 用例编号与名称

TC-03 亲和 Key 返回 429 后轮换并重新绑定

## 所属场景

SC10 同 cluster 多 API-Key 会话保持

## 版本声明

- `bfe`：当前源码版本

## 测试目的

验证当已绑定的亲和 Key 返回 429 时，BFE 会切换到其他 Provider Key，并更新 Redis 中的会话绑定。

## 运行模式

单组件模式：仅启动真实 `bfe` 进程与嵌入式 Redis。

## 前置条件

1. 已编译 `bfe` 可执行文件。
2. 嵌入式 Redis 已启动。
3. mock 后端 `cluster_session_affinity` 已启动，初始返回 200。
4. 临时 BFE 配置已生成并加载，`SessionAffinity = true`。
5. `ak_session_affinity` 已建立 token 与路由绑定。

## 配置构造

- `cluster_session_affinity.AIConf`：
  - `Keys`: `[{"Name":"key-a","Key":"sk-key-a","Weight":50},{"Name":"key-b","Key":"sk-key-b","Weight":30},{"Name":"key-c","Key":"sk-key-c","Weight":20}]`
  - `KeyPolicy.SessionAffinity`: `true`
  - `KeyPolicy.SessionAffinityPenaltyEnable`: `true`

## BFE 请求

第一次请求与后续请求使用相同构造：

| Host | Path | Authorization | Body |
|------|------|---------------|------|
| `session-affinity.example.org` | `/v1/chat/completions` | `Bearer ak_session_affinity` | `{"model":"gpt-4"}` |

执行步骤：

1. 发送 1 次请求，建立绑定并记录最终 Provider Key `K1`；
2. 修改 mock 后端：当 `Authorization == K1` 时返回 429，否则返回 200；
3. 再发送 20 次请求。

## 预期结果

- 后续 20 次请求全部返回 200。
- 至少有一次成功请求使用了非 `K1` 的 Provider Key。
- Redis 绑定更新为新的 Provider Key。

## 清理

停止 `bfe` 进程、mock 后端与嵌入式 Redis，删除临时目录。
