# SC07 AI 限流 Redis 键

## 1. 场景背景与目的

`mod_ai_rate_limit` 支持按规则维度对 AI 请求进行 RPM/TPM 限流。限流计数器持久化在 Redis 中，Redis 键的生成规则直接影响计数器在规则重命名、模型变更后的连续性。本场景验证：

- 当限流规则显式配置 `redis_key` 时，BFE 使用该 key 读写 Redis 计数器；
- 规则名变更但 `redis_key` 不变时，RPM 计数器保持连续；
- 规则模型变更但 `redis_key` 不变时，RPM 计数器保持连续；
- 未配置 `redis_key` 时，BFE 回退到基于规则名生成 Redis key，保持向后兼容。

## 2. 运行模式

- **单组件模式**：仅启动真实 `bfe` 进程，并启动内存 Redis 服务（由测试框架提供）。
- 不涉及 `ai-gateway-api` 与 `conf-agent`。

## 3. 涉及的 BFE 配置文件

| 文件 | 说明 |
|------|------|
| `bfe.conf` | 启用 `EnableAiGateway`，加载 `mod_ai_route`、`mod_ai_token_auth`、`mod_ai_rate_limit` |
| `mod_ai_route/mod_ai_route.conf` | 指定 `ai_route.data` 路径 |
| `mod_ai_route/ai_route.data` | 定义 apikey 级路由规则，命中 `cluster_ratelimit` |
| `mod_ai_token_auth/mod_ai_token_auth.conf` | 指定 token 规则路径 |
| `mod_ai_rate_limit/mod_ai_rate_limit.conf` | 指定限流规则路径 |
| `server_data_conf/host_rule.data` | 声明 `ai_product` 产品线对应的 Host |
| `server_data_conf/route_rule.data` | 默认路由 |
| `cluster_conf/gslb.data` | GSLB 权重配置 |
| `cluster_conf/cluster_table.data` | 运行时根据 mock 后端地址动态生成 |
| `cluster_conf/cluster_conf.data` | 运行时根据 mock 后端动态生成，包含 `cluster_ratelimit` 的 `AIConf` |

> 说明：`ai_rate_limit.data` 由测试代码在运行时根据 `rateLimitPolicy()` 动态生成，便于控制规则名、模型与 `redis_key`。

## 5. 测试例列表

| 编号 | 名称 | 核心验证点 |
|------|------|------------|
| TC-01 | 规则重命名后 RPM 计数器保持连续 | 使用稳定 `redis_key`，规则名变更后第二次请求仍被限流 |
| TC-02 | 模型变更后 RPM 计数器保持连续 | 使用稳定 `redis_key`，请求模型变更后第二次请求仍被限流 |
| TC-03 | 未配置 redis_key 时按规则名回退 | 无 `redis_key` 时，BFE 使用规则名生成 Redis key，行为向后兼容 |

## 5.1 测试例详细说明

### TC-01 规则重命名后 RPM 计数器保持连续

**目的**：验证 `redis_key` 优先级高于规则名，规则重命名不会导致计数器重置。

**请求构造**：

| 字段 | 值 |
|------|-----|
| Host | `ratelimit.example.org` |
| Path | `/v1/chat/completions` |
| Header | `Authorization: Bearer ak_ratelimit` |
| Body | `{"model":"gpt-4"}` |

**执行步骤**：

1. 启动 BFE，限流规则名为 `old-rule`，`redis_key = RL_RPM_rlp-0001_0`；
2. 发送第一次请求，预期 200；
3. 发送第二次请求，预期 429；
4. 停止并重启 BFE，限流规则名改为 `new-rule`，`redis_key` 保持不变；
5. 发送第三次请求，预期仍为 429。

**预期结果**：

- 三次请求分别返回 200、429、429。
- `cluster_ratelimit` mock backend 被命中 1 次。

### TC-02 模型变更后 RPM 计数器保持连续

**目的**：验证 `redis_key` 不变时，模型变更不会导致计数器重置。

**请求构造**：

| 步骤 | Body |
|------|------|
| 1 | `{"model":"gpt-4"}` |
| 2 | `{"model":"gpt-4"}` |
| 3 | `{"model":"gpt-3.5"}` |

**执行步骤**：

1. 启动 BFE，限流规则模型为 `gpt-4`，`redis_key = RL_RPM_rlp-0001_0`；
2. 发送两次 `gpt-4` 请求，第一次 200，第二次 429；
3. 停止并重启 BFE，限流规则模型改为 `gpt-3.5`，`redis_key` 保持不变；
4. 发送 `gpt-3.5` 请求，预期仍为 429。

**预期结果**：

- 三次请求分别返回 200、429、429。
- `cluster_ratelimit` mock backend 被命中 1 次。

### TC-03 未配置 redis_key 时按规则名回退

**目的**：验证未配置 `redis_key` 时，BFE 回退到基于规则名生成 Redis key。

**请求构造**：

| 字段 | 值 |
|------|-----|
| Host | `ratelimit.example.org` |
| Path | `/v1/chat/completions` |
| Header | `Authorization: Bearer ak_ratelimit` |
| Body | `{"model":"gpt-4"}` |

**执行步骤**：

1. 启动 BFE，限流规则名为 `name-based-rule`，不配置 `redis_key`；
2. 发送第一次请求，预期 200；
3. 发送第二次请求，预期 429。

**预期结果**：

- 两次请求分别返回 200、429。
- `cluster_ratelimit` mock backend 被命中 1 次。

## 6. 公共基础设施

本场景使用测试框架内置能力：

1. **`common/redis_server.go`**：启动内存 Redis 服务，供 `mod_ai_rate_limit` 连接。
2. **`common/bfe_config_builder.go`**：根据 `RateLimitPolicyData` 动态生成 `ai_rate_limit.data`。

## 7. 与其他场景的依赖关系

- 依赖 SC01 已验证的 `mod_ai_route` 路由表查找与绑定能力；
- 依赖 SC02 已验证的多 API-Key 基础能力；
- 不依赖 SC03 的 RMB 配额扣减逻辑。
